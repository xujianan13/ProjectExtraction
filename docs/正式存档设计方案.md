# 正式存档设计方案

状态：首版已按本方案实施；本文保留设计决策，当前 API 与验收范围以[使用指南](正式存档使用指南.md)和[验收记录](正式存档验收记录.md)为准。核对日期：2026-09-26。

## 1. 结论与现状

新增独立 `ISaveModule`，采用“游戏数据 → 存档会话 → 双槽仓库 → 平台存储适配器”的结构。游戏只使用统一存档 API；原生文件、浏览器 IndexedDB、小游戏平台存储 API 的差异由适配器处理。

现有 `IStorageModule` / `StorageSpace` 继续负责音量、画质、输入绑定等偏好。它们是同步接口，`PlayerPrefsStorageSpace.GetObject` 在反序列化失败时返回默认值，无法区分新玩家、坏档与存储访问失败，不适合作为正式存档的默认后端。

本方案参考 HTML 框架实际的 `SaveCoordinator`、`SaveSession`、`SaveRepository`，沿用双槽、迁移、显式激活、恢复确认和在途写入保护；按 Unity 的主线程、UniTask、热更启动和应用生命周期重新接入。

## 2. 职责与代码归属

| 层级 | 拟议类型 | 职责 |
| --- | --- | --- |
| 游戏层 | `SaveDefinition<T>`、游戏 DTO、版本迁移 | 默认数据、持久字段、各版本校验与迁移、恢复玩法状态 |
| 模块层 | `ISaveModule` / `SaveModule` | 配置后端、打开会话、同身份单写者保护、生命周期接入 |
| 会话层 | `SaveSession<T>` | 激活、快照、dirty/revision、自动保存合并、Flush/Close、状态通知 |
| 仓库层（内部） | `SaveRepository` / `SaveEnvelope` | A/B 记录、身份/校验和/版本检查、候选提交、读回确认、恢复 |
| 存储端口 | `ISaveBackend` | 异步读取、写入及完成确认、错误映射；不理解金币、关卡等游戏数据 |
| 平台实现 | `FileSaveBackend`、`IndexedDbSaveBackend`、小游戏适配器 | 调用文件系统、浏览器或平台 SDK |

拟议目录：

```text
Assets/Scripts/GameFramework/Runtime/Modules/Save/
    Contracts/       接口、策略、结果和状态
    Session/         自动保存与会话
    Repository/      双槽、封装、恢复
    Backends/        原生文件、内存测试后端
Assets/Scripts/GameFramework/Platforms/WebGL/
    Runtime/         C# 适配器
    Plugins/         IndexedDB .jslib 桥接
Assets/Scripts/PlatformAdapters/
    WeChat/          依赖所选微信 Unity SDK 的适配器
    Douyin/          依赖所选抖音 Unity SDK 的适配器
Assets/Scripts/GameLogic/Runtime/Save/
    PlayerSaveData.cs
    PlayerSaveDefinition.cs
    Migrations/
    PlayerSaveService.cs
```

通用模块不引用 `GameLogic`、`Boot` 或具体小游戏 SDK。平台 SDK 适配代码使用独立 asmdef 和平台条件；未安装 SDK 的 Editor 工程也能编译。将来整理 package 时，可直接带走通用存档模块和通用平台适配器。

`GameEntry.RegisterDefaults()` 注册空闲 `SaveModule`；启动层选择并配置后端；热更程序加载后再注册游戏存档定义、打开会话。框架初始化不创建玩家默认档。

## 3. 跨平台存储方式

| 环境 | 默认实现 | 如何判断写入完成 |
| --- | --- | --- |
| Editor | `FileSaveBackend`，使用独立开发命名空间 | 文件写入、flush/关闭完成，再读回校验 |
| Windows / Android / iOS 等原生包 | `FileSaveBackend`，根目录为 `Application.persistentDataPath/Saves` | 同上；可用平台的临时文件与替换操作作为附加保护 |
| 标准 WebGL 浏览器 | `IndexedDbSaveBackend`，C# → `.jslib` → IndexedDB | 等待事务 `complete`，再读回；单次 `put` 的 success 不作为最终成功 |
| 微信 / 抖音小游戏 | 对应 SDK 适配器，将完整记录作为字符串交给平台本地存储 API | 等待 SDK 约定的完成回调，再读回；失败和不存在分别映射 |
| 自动化测试 | `MemorySaveBackend` / 故障注入后端 | 模拟延迟、损坏、配额、失败和迟到完成 |

原生持久目录位置由 Unity 提供；WebGL 的 `persistentDataPath` 则属于 IDBFS 路径，因此不能把浏览器虚拟文件写完等同于已经完成持久化。本方案首版选择直接 IndexedDB 桥接，使存档事务的完成边界更明确。[Unity 2022.3 持久目录说明](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Application-persistentDataPath.html)、[IndexedDB 事务完成语义](https://www.w3.org/TR/IndexedDB-2/#idbtransaction)

如果以后改用 IDBFS，也必须由该后端串行管理同步与完成回调，不能只返回 `File.WriteAllText` 的结果。[Emscripten 文件系统说明](https://emscripten.org/docs/api_reference/Filesystem-API.html#FS.syncfs)

小游戏首选 SDK 的本地键值存储；大存档项目可以换成其文件系统适配器，上层协议不变。例如抖音 `tt.setStorage` 是异步本地缓存 API，存在单键与总容量限制，适配器必须映射配额错误。[抖音官方说明](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/api/javascript-api/data-caching/tt-set-storage)

平台选择由项目启动配置明确指定。小游戏即使编译目标是 WebGL，也优先使用对应小游戏适配器；不能仅凭 `UNITY_WEBGL` 自动选浏览器实现。缺少适配器返回 `Unsupported`，不得静默退到内存并显示保存成功。

### 后端最小契约

- `InitializeAsync`：建立连接/检查路径与能力。
- `ReadAsync(key)`：区分 `Found`、`Missing`、访问失败；返回完整记录字符串。访问异常不是 `Missing`。
- `WriteAsync(key, record)`：只修改这个键/文件；完整等待该后端可提供的提交边界。只有确定停止的操作才能报告结束。
- 能力信息：稳定 `StorageIdentity`、单条大小上限（未知可不提供）、存储可用状态。记录编码、大小限制与平台的容量计算由适配器对齐。
- 管理清理接口单独提供，只清理给定存档身份；常规保存不需要删除或多键事务。首版不提供跨空间的 `DeleteAll`。

公共操作使用 `UniTask` 和结果类型；可预期的缺档、配额不足、不可用等直接返回错误码。文件/SDK 边界只捕获确有必要转换或恢复的异常，通过 `ILogModule` 记录摘要。

“成功”表示平台所提供的持久化接口已完成且内容读回一致，不额外承诺平台未提供的断电耐久性。所有适配器都必须满足：写一个逻辑记录不能破坏另一个记录。

## 4. 身份、数据与格式

每份逻辑存档由 `GameId + Environment + ProfileId + SlotId` 标识。默认可使用 `guest/main`，登录/切换用户时显式更换 Profile；不隐式把游客档归入登录账号。

底层路径或键统一构造，示意如下：

```text
saves/v1/<game>/<environment>/<profile>/<slot>/a
saves/v1/<game>/<environment>/<profile>/<slot>/b
saves/v1/<game>/<environment>/<profile>/<slot>/pre-migration/a
saves/v1/<game>/<environment>/<profile>/<slot>/pre-migration/b
```

各段需要编码、长度限制和身份校验；原生路径必须限制在配置的存档根目录内。游戏版本、AB 包版本不参与存档路径，避免每次更新都变成“新玩家”。Editor 与发布环境分开；浏览器数据库名称保持稳定。

`Resources` / `GameResources` 只保存资产或默认配置，不保存玩家运行数据。YooAsset 缓存与存档分开命名和清理。

统一封装包含：`formatVersion`、完整身份、`schemaVersion`、`sequence`、`savedAtUtc`、`payloadJson`、`checksum`。可记录写入程序版本供诊断，但不参与新旧排序。

- `formatVersion` 是框架封装版本；`schemaVersion` 是游戏数据结构版本。
- `sequence` 是持久化递增序号；新旧判定不依赖设备时间。
- `payloadJson` 保存游戏快照的原始 JSON 字符串，平台适配器作为不透明记录传递，避免 JS 重解析导致数值或格式变化。
- 校验和使用 SHA-256，覆盖版本、身份、序号、时间和 payload 的确定编码字节。编码必须固定字段顺序、长度与数值格式，读取时不重新序列化 DTO 来计算校验和。
- 校验和用于识别截断和损坏；不承担防作弊职责。
- 默认每条完整记录上限建议 256 KiB，可配置；A/B 两份常规记录、最多两份迁移备份及原生临时文件都计入容量预算。不能仅检查 payload 大小。

游戏提供普通可序列化 DTO，保存关卡 ID、配置 ID、数值和列表等必要字段。Unity 对象引用、Transform、资源句柄、委托和运行时服务不进入存档；恢复时依据 ID 重建。

首版提供基于现有 `JsonUtility` 的 codec，沿用项目现有依赖；游戏显式声明可序列化字段与各历史版本 DTO。复杂字典/多态需求可替换 `ISaveCodec<T>`。不引入程序集扫描；热更 DTO 的序列化、迁移与泛型调用需纳入 IL2CPP/HybridCLR 样例验收。

## 5. 可靠写入与恢复

### 双槽协议

假设 A 是当前有效记录，序号为 20：

1. 在主线程取得独立快照及其 revision，完成数据校验和编码。
2. 构造序号 21 的完整记录，目标选择 B。
3. 向 B 写入，等待后端提交完成。
4. 重新读取并核对候选记录，同时检查 A/B 是否出现冲突记录。
5. 确认成功后更新会话保存基线。A 仍保留序号 20；下一次写入才使用 A。

不额外写一个“当前槽指针”。读取时检查两份完整记录，选择有效且序号最高的一份，避免要求小程序支持跨 key 原子事务。

完整、有效的新记录一旦持久化就可能在下次启动时被选中，即使本次运行在成功回调前被结束。因此取消等待或回调超时不代表没有写入。

原生后端可先写目标槽的临时文件、flush，再替换目标槽；缺少可靠替换原语时，仍只能写非当前槽。通用恢复机制依靠 A/B，不能依靠所有平台都支持 `File.Replace`。临时文件不作为已提交记录读取。

### 读取结果

| 情况 | 处理 |
| --- | --- |
| A/B 及迁移备份都确定不存在 | 校验后生成默认数据，暂不落盘 |
| 至少一份有效，其他为不存在或较旧有效记录 | 选择有效最高序号，正常读取 |
| 一份损坏、另一份有效 | 返回 `Recovered` 和可恢复数据；项目确认后才能激活写入 |
| 两份损坏 | 返回 `Corrupt`，保持原记录；不自动用默认档覆盖 |
| 读取介质失败 | 返回 `ReadFailed`，允许相应重试；不创建默认档 |
| 遇到未来 schema / 不支持的封装 | 返回 `VersionTooNew` / `FormatUnsupported`，阻止写入 |
| 相同序号但内容不同 | 返回 `Conflict`，阻止自动选取和覆盖 |
| 缺迁移步骤或迁移校验失败 | 返回 `MigrationFailed`，保留原记录；不伪装为坏档回退 |

即使另一个槽更旧且可读，也不能通过跳过未来版本来自动开启旧程序写入。若常规槽都缺失但存在迁移备份，同样进入恢复流程，不能直接判断为新玩家。

恢复确认使用显式 API，通常由游戏 UI 提示后调用 `AcceptRecovery`；项目也可以明确配置自动接受备份策略。重新开始应使用新的逻辑 Slot 或显式归档/重置操作，不能通过普通 `OpenAsync` 清空坏档。

### 串行、超时与失败

- 同一 `StorageIdentity + 存档身份` 在进程内只允许一个写入会话；不同后端实例指向同一存储空间也不能绕开占用。
- 写入期间的后续变更只标记更高 revision，合并到下一次保存。
- 区分 `NotCommitted`、`Committed`、`Uncertain`。配额/参数/过大等确定失败直接返回；瞬时 I/O 失败按策略重试。
- 调用方超时或取消只结束等待；已提交给文件/SDK 的写入仍由内部任务跟踪，保留身份占用。底层未结束前不得重试、改写另一槽或释放后重新打开同身份。
- 底层结束后按候选身份、序号和校验值重新核对。只有确认未提交，才允许创建下一次重试；无法确认保持 `Uncertain` 并等待恢复条件。
- 读回一致只能证明对应后端边界的结果，不通过内存缓存的回显伪造持久化确认。
- 跨进程、跨浏览器标签页的并发写入首版不承诺互斥；发现冲突停止写入。需要同时运行多个客户端时，再增加对应平台锁或服务端版本控制。

## 6. 数据迁移与热更启动

游戏维护明确的 `v1 → v2 → v3` 迁移链。先校验来源版本，再在独立数据上逐步迁移，每一步校验目标版本；全部成功才恢复游戏状态。迁移只处理数据，不访问场景、网络或存储。

迁移成功不立即改写原档。启动流程拟调整为：

```text
Framework 初始化 → 选择平台后端 → 热更完成
→ GameLogic 定义存档 / OpenAsync / 在内存迁移
→ 恢复玩法状态 / 完成必要初始化
→ GameMain.StartAsync 返回 → Boot CommitReady
→ 项目启动成功通知 → SaveSession.Activate
→ 创建迁移备份（需要时）→ 必需首存成功
→ 游戏存档就绪 → 开放玩法进度 / 退出 Loading
```

当前 Boot 在 `LaunchGameAsync` 成功后执行 `CommitReady`。实施时补项目启动成功通知，GameLogic 在此通知后显式激活已准备好的会话。`GameMain.StartAsync` 内不等待该通知触发的保存，避免启动互相等待。启动期间也不开放会产生玩家进度的操作。

实施时由项目 `PlayerSaveService` 持有明确的 `IsReady` 状态，在打开场景前取得 `IInputModule.BlockGameplay` 句柄；场景激活阶段只恢复/初始化，玩法启动与持久状态变更入口等待 IsReady。新建/迁移档首存成功，或原有正常存档完成激活后，才标记就绪并释放输入阻断、退出 Loading。普通读取无待保存变化时无需制造一次写入。仅阻断输入不够，模型变更和场景自动玩法也必须遵守该状态。

未确认恢复、迁移失败或初始化失败的会话不能激活。程序 Ready 与存档 Ready 分开：前者允许 CommitReady，后者控制进入游戏。首次保存失败时维持 Loading/存档错误 UI 和进度阻断，只重试存档收尾；不走再次加载 DLL 的热更重试分支。启动收尾需由项目层等待存档就绪，SaveModule 不引用 Boot 或 GameLogic。

新建档和成功迁移的数据在激活时自动标记为待保存。首次保存失败保留当前内存状态和失败结果；首版样例保持进度阻断，直到重试成功或退出本次启动。

### 迁移前备份

A/B 保存的是最近两次提交，连续保存后两份都可能变成新 schema，因此增加独立 `pre-migration` 记录。这是针对本项目热更回退新增的保障，HTML 当前实现没有该独立备份：

1. 第一次提交更高 schema 前，保存本次迁移来源的完整旧记录，等待持久化并读回确认。
2. 迁移备份自身也使用 A/B 轮换：只写非当前备份槽，以来源存档的序号和校验值识别候选；已有相同记录时复用。新备份确认前，保留上一份已确认备份。
3. 备份成功才允许写入新 schema 的常规 A/B；备份失败时保留旧档并暂停迁移提交。
4. 平常自动保存不修改迁移备份。容量固定为两个备份槽，可保留最近两次升级来源；不要求每份存档都已有两次历史升级。备份仅供显式恢复，不参与正常 A/B 的最高序号选择。
5. 未来版本档存在时默认阻止旧程序写入；读取迁移备份必须显式恢复。首版恢复到新的 Slot，保留新版本 A/B，避免丢掉升级后产生的进度。

恢复入口单独定义：`InspectRecoveryAsync(identity)` 只检查常规记录和迁移备份，返回来源、schema、序号、校验值及是否可供当前程序恢复；`RestoreToNewSlotAsync(candidateId, newSlot)` 重新校验候选和空目标，取得目标写入占用并生成待激活的恢复会话。目标不是空存档就返回冲突；确认选择该候选视为接受这次恢复，恢复数据在启动就绪后的首次保存才写入目标。普通 `AcceptRecovery` 只确认 OpenAsync 已选出的 A/B 恢复结果，不会暗中选择迁移备份。

热更包回退与存档回退是两个独立动作。首版支持检测不兼容、保留旧数据和明确恢复，不承诺任意旧代码能够无损继续玩新版存档。需要更多代历史回退的游戏，可扩展备份保留策略。

## 7. 自动保存与应用生命周期

建议首版默认策略（均可配置）：

| 时机 | 行为 |
| --- | --- |
| 持久数据变化 | 游戏调用 `MarkDirty`，增加 revision |
| 连续变化后空闲 1 秒 | 合并保存一次 |
| 持续变化达到 10 秒 | 发起一次保存，避免一直 debounce |
| 关卡结算、重要奖励、用户手动保存 | 显式等待 `FlushAsync` |
| 进入后台 | 立即触发尽力 Flush，合并重复焦点/暂停通知 |
| 返回前台 | 检查在途任务和 dirty，按状态补保存或提示失败 |
| 切换账号、退出到标题、业务控制的关闭 | 冻结对应数据修改，等待 `CloseAsync` 成功，再切换身份/销毁数据 |

复用 `GameEntry.ApplicationBackgroundChanged`，调度使用 `ITimerModule` 的非缩放计时或注入单调时钟。`Time.timeScale = 0` 不应阻止保存；系统挂起后不假定仍有帧或回调。

小游戏 SDK 的 hide/show 信号通过项目生命周期适配器接入同一存档通知路径，并与 Unity 信号去重；不能假定所有导出 SDK 都会完整转发 Unity 焦点事件。

`FlushAsync` 等待调用时的目标 revision 被确认保存，并返回 sequence / targetRevision / savedRevision。保存期间发生的新变化仍保持 dirty，不会被旧完成回调清除。普通自动保存失败保留 dirty；瞬时错误建议最多 3 次退避重试，配额不足、数据无效、未来版本和结果不确定不进入盲目重试。

`CloseAsync` 可等待收束；同步 `Dispose` / `OnShutdown` 只做清理，不宣称保存成功，也不使用 `.Wait()` 阻塞主线程。已在途操作在安全结束前保持底层占用并自行收尾。

自动保存是主要保障，退出回调只作补充。Unity 2022.3 文档说明 WebGL 无法按普通方式实现 `OnApplicationQuit`，移动平台挂起后被系统结束时也可能没有该回调。[Unity 退出生命周期说明](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/MonoBehaviour.OnApplicationQuit.html)

快照构建和 Unity 数据访问在主线程完成，形成独立 DTO/记录后才允许原生后端做异步 I/O；通用协议不依赖 `Task.Run`，浏览器和小游戏使用各自回调驱动。默认不每帧序列化整个存档。

## 8. 游戏侧最小接入面

游戏只需提供：

1. `PlayerSaveData`：需要持久化的 DTO。
2. `PlayerSaveDefinition`：当前 schema、默认值、各版本校验与迁移。
3. `PlayerSaveService`：从存档恢复游戏模型、生成独立快照，在持久字段变化时调用 `MarkDirty`。

拟议公开操作：

| 操作 | 语义 |
| --- | --- |
| `ISaveModule.ConfigureBackend` | 首次打开会话前选择平台实现；存在会话时禁止直接换后端 |
| `OpenAsync<T>` | 读取/校验/在内存迁移，返回结果与尚未激活的会话 |
| `BindSnapshot` | 绑定游戏快照生成器；按保存时机调用 |
| `AcceptRecovery` | 接受 OpenAsync 已选出的 A/B 恢复结果 |
| `InspectRecoveryAsync` / `RestoreToNewSlotAsync` | 明确选择迁移备份，校验后恢复到新的空 Slot |
| `Activate` | 项目初始化成功后允许保存 |
| `MarkDirty` | 持久数据已改变，增加 revision 并调度保存 |
| `FlushAsync` / `RetryAsync` | 等待保存回执；Retry 遵守确定失败/未知结果区分 |
| `CloseAsync` | 等待最终保存与操作收束后关闭 |
| `GetStatus` / 状态通知 | 查询未激活、保存中、失败、不确定、已关闭及 dirty 状态 |

不要求项目先引入统一 StateStore 或改写所有 Model。相互关联的金币、道具与任务数据首版放在同一逻辑存档快照中，跨 Slot 不提供原子事务。框架不直接弹 UI，由现有 UI 系统根据结果展示恢复、重试或更新提示。

## 9. 首版实施与验收范围

1. **通用核心**：封装、A/B、迁移与迁移备份、错误结果、会话单写者、自动保存与 Flush/Close。
2. **可直接开发的默认实现**：Editor/原生文件后端、隔离开发档、GameLogic 样例和现有启动/生命周期接入。
3. **WebGL 实现**：独立 IndexedDB 桥接；实际浏览器验证刷新、关闭重开、拒绝存储和配额失败。
4. **小游戏接入层**：通用异步 KV 适配契约及微信/抖音接入模板。具体 SDK 安装后补全其版本对应的桥接并做开发者工具与真机验证；模板和替身测试不算平台已经可用。

首版必须验证的行为：

- 缺档与读失败区分；身份隔离；A/B 交替、截断损坏、旧备份恢复与恢复确认。
- 写失败、写完后回调失败、超时后迟到完成、取消等待、关闭中写入、重复打开同身份。
- 写入过程中 revision 增长不会丢 dirty；暂停计时、切后台重复事件、恢复后的补保存。
- 连续版本迁移、迁移失败不改原档、未来版本不覆盖、启动失败不激活、迁移备份失败不提交。
- 原生实际文件的进程重开恢复；WebGL 实际 IndexedDB 的浏览器重开恢复。
- IL2CPP/HybridCLR 下游戏 DTO 与迁移代码可工作；具体小游戏 SDK 的真实完成/失败/配额语义单独验收。

云同步、跨设备合并、跨客户端并发写、透明存整个场景、多代历史归档作为后续扩展。当前目标是提供拿来即用的本地正式存档，特殊游戏需求可直接改源码。
