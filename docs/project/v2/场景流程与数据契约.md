# 场景流程与数据契约

更新日期：2026-10-12。适用版本：v2。本文承接单局协调、保存事务与结果展示的基础约束，并将多区域、独立奖励队列和收藏接入同一流程。现有类名用于定位改造入口；下文新增的业务阶段和数据职责尚未实现，不代表已有 API 或验收结果。

## 1 状态与所有权

一关使用一个稳定的 RunId，区域切换不创建新局、不重复扣体力、不提前结算物品。操作代次用于拒绝同局中过期的加载、交互和返回回调，不能代替 RunId。

| 权威对象 | 负责状态 | 约束 |
| --- | --- | --- |
| ProjectRunCoordinator | 准入、加载、激活、终局、失败恢复和返回 Home | 唯一流程入口，协调现有 GameRoundFlow，不新增平行的单局框架 |
| ProjectSession | 局外档案、待保存候选、修订号和确认状态 | 钱包、物品、成长、体力和结算通过同一项目保存入口串行提交 |
| ExpeditionRun | 本关计划、当前区域、战斗协调、交互和奖励队列 | 消费战斗事实，不让场景销毁决定收益或结局 |
| 区域运行状态 | 敌人、箱子、商人、物品及目标完成情况 | 与区域表现对象分开；表现重载不重抽内容或重置领取状态 |
| Home 与 Expedition 逻辑场景 | 所属场景的资源、表现和就绪信号 | 退出只释放自己拥有的对象，不发奖或直接改写结算 |
| 全局流程窗口 | 加载、保存、失败、已保存结果和返回操作 | 即使当前逻辑场景为空，也应保留可操作的恢复入口 |

固定宿主继续使用 Main、Loading 和 Framework.prefab；Home 与 Expedition 是逻辑场景。区域可在 Expedition 内独立加载，不要求为每张区域新增一个 Unity 场景或重新启动热更框架。

## 2 入场和激活

1. Home 就绪且没有未决保存、活动关卡或待恢复结果时，才允许开始新局。按钮禁用只负责提示，业务入口仍要检查状态。
2. 校验内容配置、关卡与装备等级、体力、携入实例归属和已学技能；锁定本次出战，生成同一份关卡身份、随机计划与最终 Boss。
3. 将入场记录、一次体力扣费和携入物品托管纳入同一保存候选。仅在回执确认目标修订后发布成功；失败或结果不确定时重试原候选，不重建种子或再次扣费。
4. 准备当前区域、角色、相机、表现、HUD 和输入上下文。准备期间关闭 ECS 推进及玩法输入，防止不可见角色受伤。
5. 场景 Ready、框架单局加载调用完成且不再 Busy、运行授权保存确认后，才激活模拟、自动攻击与交互。触屏轴和待执行交互应从空状态开始。

现有代码的持久阶段为 Admitted、Running、OutcomeRecorded；它们可作为改造起点。Running 只是已保存的开始授权，不证明第一帧一定执行过。加载失败退款、跨体力重置的补偿方式和正式强退政策仍需按[模块职责与开发验收](模块职责与开发验收.md)中的待定项确定，不能把开发期退款当成正式玩法。

## 3 区域切换和奖励门禁

v2 的区域推进条件由[整体设计](多区域探索与成长奖励整体设计.md)确定：区域内连续探索，尾王完成后允许结束或继续；是否回访前一区域仍按 D5 确认。旧版“未清房也可任意去相邻房间”的出口规则不再使用。

区域转换需要同时检查当前 RunId、区域身份、操作代次、角色状态、尾王完成情况和未决奖励。已经产生的奖励选择应先兑现；一个转换请求只能提交一次当前区域变化。

目标区域准备失败时，必须保留本关权威数据并提供明确恢复入口，不能伪造撤离或重新开局。角色生命、Buff、冷却、技能和刷怪余量的跨区域具体继承规则仍由 D7 确认；无论采用哪种规则，都不能因表现重载意外重置或复制。

| 奖励职责 | 权威来源与提交边界 |
| --- | --- |
| 技能进度 | 消费已去重的敌人死亡事实；普通和精英贡献不同，不能根据飘字、动画或旧 RoomCleared 触发 |
| 技能选择 | 达阈值产生独立资格；候选只含当前技能池允许的效果，已兑现选择只记一次 |
| Boss 战利品 | Boss 身份、来源与轮序号确定唯一批次；展示的是已冻结具体物品候选 |
| 领取 | 业务层验证当前批次、轮次和候选，成功后移动物品或应用技能，再推进队列；窗口只提交意图 |
| 暂停 | 一个选择窗口结束而仍有待选资格时继续暂停；不得误解除背包、手动暂停或应用后台原因 |

同 tick 玩家死亡与 Boss 死亡的仲裁、资格队列顺序、最终 Boss 召唤物是否贡献进度，均保持整体设计第 5.4 节的建议状态。开发时必须显式确定这些规则，不能直接用旧“Boss 死亡立即完成单局”的调用路径。

## 4 终局和结算

需要区分提前成功结束、最终通关、死亡和主动放弃。现有 Extracted、Abandoned 字段是迁移起点，不足以表达所有 v2 状态；正式数据表示在 P3 确定，不能仅凭一个 Won 或 bool 推断全部奖励。

成功终局的流程为：完成应得选择 → 冻结完整结果 → 保存终局事实 → 退出战斗资源 → 统一保存收益 → 展示已到账结果。最终 Boss 奖励全部兑现之前不得冻结一份缺少奖励的通关结果。死亡或放弃按确定的结局策略冻结，不借胜利队列额外领取物品。

沿用以下保存约束：

- 终局只接受一次；冻结后停止后续 tick、拾取、购买、换装和区域转换，旧局迟到事件不能影响下一局。
- 冻结结果是独立纯数据，不引用 CombatWorld、GameObject、窗口或可继续变化的物品集合。
- 先记录终局事实，确认后才交给 GameRoundFlow 退出与结算；一次通知被发出不代表框架已经接纳，协调层应确认身份和阶段。
- 入库/损失物品、尚未提交的经验与技能点、实际交易增量、按 D8 应在本次处理的收藏登记及成就、结束标识和战绩一起形成结算候选。已经确认的增量不能重复应用或被旧快照覆盖。
- 保存回执覆盖本次修订后才发布成功与最终局外数据。Flow 保存回调正常返回表示保存成功，不能只记错误日志后仍返回成功。
- 保存失败重试同一候选、同一随机结果和同一结算身份，不重抽装备、不再次加属性、不创建第二份物品。

收藏登记时机、安全箱资格及死亡时哪些藏品实际入库仍由 D8 决定。死亡打怪经验与局内钱包政策不能从“箱外物品丢失”推导；相关未定规则见[基础玩法与局外成长](基础玩法与局外成长.md)。

## 5 结果页和返回

结果页展示已经确认保存的结局、物品去留、经验、等级、技能点、交易、收藏与成就变化。Boss 领奖窗口发生在结算前，结果页按钮不承担再次发奖。

返回时先收束框架单局状态，再加载 Home，绑定最新档案并确认就绪，最后保存结果已查看标记并开放局外操作。Flow 的 Menu 不等于 Home 已加载；冷启动恢复结果时 Flow 可以已经是 Menu，不能强制重新进入一局才能展示或返回。

结果页打开失败、Home 加载失败或查看标记保存失败，分别重试对应步骤，不重做结算。返回后不自动出售携回物品，不随机重做词条，不暗中恢复已经损失的装备。

## 6 中断与恢复

| 中断位置 | 必须保留与恢复的内容 | 不得发生的行为 |
| --- | --- | --- |
| 入场写入结果不确定 | 原 RunId、候选与修订；先确定是否提交 | 未确认就重扣、退款或创建第二份携入物品 |
| 场景加载或运行授权失败 | 已确认入场记录及资源清理状态 | 未 Ready 时推进战斗，或把加载失败算死亡 |
| Boss 正在领奖 | 已确定批次、轮次、候选、已领取结果与尚待领取部分 | 恢复后重抽或重发；直接跳过剩余奖励通关 |
| 终局记录保存失败 | 世界保持冻结，同一份待保存结果 | 继续游玩后再提交旧结果 |
| 终局已记录，退出或结算失败 | 原终局事实、结算身份和未决候选 | 回到开发退款路径、重建战斗或重复入账 |
| 已结算但未查看结果 | 已保存结果和查看状态 | 再次执行收益结算 |
| 游玩中断，尚无完整检查点 | 按已确定中断政策处理 | 声称只用 Seed 或已选技能即可恢复整关 |

P3 必须设计最终领奖的持久恢复；P6 的完整续关需要另存关卡计划、区域/敌人、角色、技能、进度、交互与随机状态，且在 D9 确定粒度后实施。现有 Running 中断后返还原装备和体力的开发策略不作为 v2 交付承诺。

保存重试与恢复应按失败阶段路由。不能将所有按钮都接到 Flow.RetryAsync，因为加载失败和已有结果失败的语义不同。退出应用、取消、手动放弃和正常结束也不是可相互替换的操作。

历史存档是否迁移遵循 D11；若决定迁移，数据映射与有效性校验应一次性完成，不保留 v1 玩法运行分支。本轮不删除真实存档。

## 7 单局统计与战绩

继续采用可追溯的实际事实：有效游玩时间由战斗逻辑时钟累计，暂停和死亡展示等待不计；伤害使用实际扣血，治疗使用实际恢复生命，零伤害、过量伤害和满血治疗不重复计入。统计随终局冻结，结果页不能从已经销毁的场景重新计算。

v2 统计需按真实奖励身份区分技能选择次数、Boss 战利品轮次、普通/精英/区域尾王/关卡 Boss 击杀，以及完成区域和提前结束/最终通关。旧“Boss 房内击杀”和“清空战斗房数”不能继续代替这些概念。

物品估值读取生成时冻结的 SellGold，表示回收参考值，不向金币钱包入账。沿用资产变化口径：携回物品回收估值 − 入场物品回收估值 − 本局实际购买支出；丢失估值仅展示，不重复扣减。若以后加入局内出售或新的币种支出，需要明确扩展统计公式。

最近战绩容量由配置决定；历史记录、结算收益和首次结算候选的时间一起保存，并按 RunId 去重。缺少某字段的记录显示未记录，不伪造零值；是否读取 v1 记录仍由 D11 决定。统计汇总应显示有效样本数，不能把保留样本当作全部玩家数据。

配置评估工具还需随 P1～P3 改为区域和独立奖励池口径，移除旧房间全清估计。固定种子、配置指纹、理论回收价和实际生成采样可继续使用；旧地图采样、理论利润与自动化通过不代表 v2 节奏、经济或玩家体验成立。

## 8 改造入口和验收

- [ProjectRunCoordinator](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Project/ProjectRunCoordinator.cs)、[ExpeditionRoundSession](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Project/ExpeditionRoundSession.cs)：流程与 Ready 门禁。
- [ProjectSession](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Project/ProjectSession.cs)、[ProjectRunRecords](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Project/ProjectRunRecords.cs)：保存候选、持久阶段和终局数据。
- [ExpeditionRun](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Gameplay/Expedition/ExpeditionRun.cs)：当前战斗与区域协调改造位置。
- [ProjectRunStatistics](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Project/ProjectRunStatistics.cs)、[ProjectRunHistory](../../../DevProject/Assets/Scripts/GameLogic/Runtime/Project/ProjectRunHistory.cs)：统计与战绩数据。
- [ProjectBalanceReport](../../../DevProject/Assets/Editor/ProjectDiagnostics/ProjectBalanceReport.cs)、[ProjectLootBalance](../../../DevProject/Assets/Editor/ProjectDiagnostics/ProjectLootBalance.cs)：现有配置指纹、理论估值与生成采样工具。非 Play 时从 Tools → ProjectExtraction → Export Balance Report 导出；当前仍统计旧地图，P1～P3 改造前不能作为 v2 数值报告。

对应阶段至少验证：Ready 前零 tick；同局不重扣；旧回调隔离；奖励候选冻结和重复领取拒绝；最后一轮完成才结算；保存失败与重启只应用一次；返场失败仍可操作；实际物品、成长、收藏和战绩一致。新的阶段结果写入 v2，旧报告只用于定位已有测试和故障场景。
