# 模块职责与开发验收

更新日期：2026-10-12。适用版本：v2。本文定义各模块的责任、数据交接、开发前需要确定的事项与阶段完成条件。模块名称是设计分工，不能据此假定某个接口或类已经存在。

## 1 开发依据

当前开发先读[整体设计](多区域探索与成长奖励整体设计.md)，再读对应基础规范：

- [基础玩法与局外成长](基础玩法与局外成长.md)：属性、物品、背包、安全箱、经济、技能与体力。
- [战斗系统与表现契约](战斗系统与表现契约.md)：战斗事实、时序、效果、动画和反馈。
- [场景流程与数据契约](场景流程与数据契约.md)：入场、奖励、终局、保存恢复及战绩。
- [工程配置与平台接入](工程配置与平台接入.md)：配置、资产、界面输入、运行构建与平台验证。

用户后续明确决定优先。整体设计中的 v2 地图、成长和奖励变更优先于旧行为；基础规范明确承接的规则继续有效。现有代码与配置说明实现起点，不能反向把示例数值或待定事项变成产品决定。v1 仅作为历史来源，不要求开发者从多个历史段落自行拼接当前规则。

## 2 模块分工

沿用 M01～M09 编号，调整旧房间职责；不额外创建第二套 v1 模块。

| 模块 | v2 负责内容 | 对外提供与边界 |
| --- | --- | --- |
| M01 单局流程与奖励协调 | 入场准入、整关身份、区域流程、刷怪进度与奖励队列、终局与恢复 | 统一阶段、奖励资格和结算候选；不计算命中或直接随机装备属性 |
| M02 角色移动与自动近战 | 输入转为移动/攻击意图、自动索敌与基础攻击请求 | 受控提交到同一 ECS 世界；不在表现 Transform 中维护第二份权威位置 |
| M03 敌人与战斗运行 | 普通、精英、尾王、最终 Boss 的战斗角色，AI、技能/飞弹/Buff 运行 | 发布已去重死亡与战斗事实；不自行打开奖励窗口、扣体力或完成关卡 |
| M04 区域生成与探索 | 区域序列、完整地图、关键点、怪群计划、目标状态与小地图投影 | 提供稳定区域身份、可达位置与进度事实；不保留旧小房间连接图作为另一路径 |
| M05 属性装备与技能效果 | 属性派生、装备/词条定义、技能候选条件与效果、弱点对应标签 | 纯数据定义和效果计算；不拥有物品位置、不直接写存档 |
| M06 物品背包与安全箱 | 装备/收藏实例、具体战利品候选、领取后归属、拾取/穿脱/容器和物品去留计划 | 唯一实例与位置；不保管局外技能点，不独立写入整局结算 |
| M07 长期成长与交易 | 经验等级、技能点、金币钻石、商店、收藏登记与成就属性 | 生成成长或交易计划，由统一项目会话保存；不重复发放已提交增量 |
| M08 界面与跨平台操作 | Home、HUD、小地图、技能/物品选择、背包商店、结果与收藏界面 | 只读业务状态并提交操作意图；不按显示文本生成奖励或替代业务校验 |
| M09 体力与时间补给 | 体力推进、每关扣费、重置和补给记录 | 提供计算与提交计划；不在每次进入区域时再次收费，不处理战斗 HP |

收藏由 M06 持有物品实例、M07 管登记与成就、M01 协调结算、M08 展示，不产生多处互相独立的发奖入口。技能进度与长期经验也分别管理：一个敌人死亡可以贡献各自合法收益，但不能共用同一个可写数值。

## 3 交接契约

以下字段名表达职责；除已存在的标识外，最终字段与 API 在实现阶段确定。

| 交接数据 | 权威维护方 | 消费规则 |
| --- | --- | --- |
| RunId、关卡身份、配置版本和计划 | M01 协调，M04 生成区域内容 | 所有跨模块请求携带归属；UI 重开、重试和区域重载不重抽本关计划 |
| 区域身份、加载/转换代次和关键目标状态 | M04，在 M01 阶段许可下修改 | 可见场景和当前区域提交一致；丢弃旧请求，不用房间序号推断 Boss 身份 |
| 实体身份、死亡事实和敌人奖励角色 | M03 | M01/M06/M07 使用同一去重事实；持续和衍生伤害造成的合法击杀不能漏记 |
| 刷怪余量、待选资格、奖励批次与轮次 | M01 | M05/M06 生成各自候选；M08 不维护独立可领取计数 |
| 技能定义/局内等级与永久技能等级 | M05 定义，M01 持有局内状态，M07 持有永久状态 | 两类成长分别应用；本关结束不清除已保存的局外技能 |
| 物品定义、实例随机属性与容器位置 | M05 定义，M06 持有实例与位置 | 一个实例同一时刻只有一处归属；显示、穿脱、保存与重试不重新随机 |
| 交易身份、库存、钱包与购买资格 | M07 协调，M06 校验物品 | 同一交易身份不可换内容；扣币、交货、库存/修订一次提交 |
| 收藏定义、已登记集合与成就属性来源 | M07，接收 M06 物品获得事实并按 D8 判断登记条件 | 实例身份不等于收藏定义身份；重复读取或收集不重复增加一次性属性 |
| 体力时间状态与扣费/领取计划 | M09 | 使用最新确认档案计算，不用旧关卡快照覆盖后来的恢复和领取 |
| 终局事实、物品/成长计划和统计 | M01 协调，ProjectSession 保存 | 同一结算只应用一次；结果页只展示已确认结果 |

小地图使用 M04 的展示投影：v2 明确要求标注区域 Boss、NPC 和宝箱，并表达已完成状态。旧“未知房间格点”和“不显示撤离候选”的规则不能用于否定 v2 已确认标注；其他揭示范围和结束入口遵循整体设计。

## 4 开发前需要确定的事项

[整体设计第 13 节](多区域探索与成长奖励整体设计.md#13-实施前待定事项)的 D1～D11 是新版机制的决策清单。它们有各自最迟确定阶段，不要求在 P1 前解决所有后期问题，也不能到实现时凭习惯填默认值。

旧系统中仍影响 v2 的未定边界应继续保留：

| 未定范围 | 现有起点与本次约束 | 最迟处理位置 |
| --- | --- | --- |
| 死亡的打怪经验、局内成长生效和钱包 | 原型有既定行为，但物品损失政策不能自动决定账户属性；已保存局外技能仍保留 | 改动相关收益前，P3 结算前统一确定 |
| 入场失败、正式强退和体力返还 | 现有 Admitted/Running 补偿只是开发策略；不以旧退款路径替代续关 | P3 流程设计，完整续关受 D9 约束 |
| 同 tick 死亡与结束/胜利 | 现有代码死亡优先；整体设计保留为建议，不能写成已获批准的玩法规则 | P1 事实收束约定，P3 终局接入 |
| 体力时区、补给可领窗口、溢出与跨日补算 | 保留时间状态与去重能力；现有参数和策略地位见基础规范 | 修改体力时钟或正式平台接入前 |
| 安全箱资格、容量单位和仓库接收能力 | 保留成功全部携出与物品唯一性；不能用未定义的容量丢弃应得奖励 | 相关物品功能前，收藏资格与 D8 一起确定 |
| 局外技能正式成本、每级点数、洗点与新技能 | 当前配置用于已有原型；洗点等未确认功能不因整理文档自动实施 | 增改局外成长前 |
| 钻石产消、广告授权与收费接入 | 钻石为独立币种，尚无已批准的产消方案；三选一刷新/第四项仍默认关闭 | 明确需求后另行实施 |
| 全失后的装备获得方式与正式经济 | 现有空装能力和金币商店是可改造起点，不能据此认定所有玩家都能无阻断循环 | P3 闭环及 P5 长期成长前复核 |

正式数值、性能目标和设备覆盖应随对应阶段记录。没有确认的功能不算已完成；没有通过的验收不通过复制历史结论补齐。

## 5 分阶段交付

| 阶段 | 文档和实现需要一起交付 | 重点验证 |
| --- | --- | --- |
| P1 刷怪进度与技能池 | 贡献/阈值与溢出规则、敌人资格、独立技能候选、队列和 HUD；删除清房概率/保底调度 | 多阈值、去重、持续/衍生击杀、无物品混入、暂停与重复选择；明确 D2/D4 和受影响的 D3/D7 |
| P2 单区域探索 | 地图模板与配置、稳定怪群、交互点、小地图、加载表现；删除旧房间连接/投影/切换职责 | 可达性、出生安全、连续探索、不重复刷新、关键点标注、路线与战斗密度；明确 D5 |
| P3 整关与 Boss 领奖 | 区域序列、整关一次体力、Boss 身份、多轮具体物品、结束/通关、领奖恢复和结算 | 不重扣/不重发/不重抽、最后一轮后结算、保存失败与恢复、死亡和放弃、收藏暂存；确定相应 D1/D3/D6/D7/D8/D9/D10 |
| P4 弱点与探索内容 | 对应技能和敌人机制、Boss 提示、宝箱商人独立池与随机库存 | 提示与实际弱点一致、多种构筑可胜、回访状态稳定、商店交易完整 |
| P5 收藏成就 | 定义/系列/登记/重复处理、永久属性来源、结果与图鉴、保存契约 | D8 定案后按确定时点登记，重复和加载不叠属性、保存一致、长期战力预算 |
| P6 续关与整关验收 | D9 确认后的检查点恢复、整关体验、平台构建与设备记录 | 同计划恢复、不复活已确认死亡、不重扣发奖、横竖屏触控、存档/资源/性能及完整关卡体验 |

D11 历史数据取舍必须在第一次改变持久化契约前确定；不能等到 P5 才处理已经发生的 schema 变化。上表表示阶段目标，不代表当前已有这些结果。

## 6 每阶段的完成条件

1. 规则可定位：对应当前文档明确采用值和行为，未定项已解决或没有进入本阶段范围。
2. 状态只有一个所有者：保存、奖励和随机计划没有 UI 副本或跨模块重复写入。
3. 旧入口已清理：被替代的 v1 专属代码、配置、资源引用和测试随阶段删除；通用能力原位复用，保留仍验证有效契约的测试并适配新场景。
4. 配置可生成：正式业务内容从 Excel 导出，schema、引用、候选池和启动校验覆盖本次变化；不存在缺配置回退硬编码。
5. 验证与变化相称：代码变动检查 Unity 编译、当前场景和受影响的 EditMode/PlayMode；完成 Prepare 后检查实际启动和对应行为。仅文档整理检查内容、链接和差异即可。
6. 记录可核对：新记录位于 v2，说明实现范围、实际执行命令、结果与剩余缺口；旧测试数、样本与平台结果不写成新验收。

不要求每阶段重复所有测试或进行 Full 模板构建。新增失败、未解决疑点或受影响公共契约需要更大覆盖时再扩大检查。自动化验证不替代战斗手感、区域节奏、经济取舍和设备操作验收。

## 7 现有已知问题与后续验证

2026-10-10 曾观察到手动退出 Play 后资源后台操作报 YooAssets 未初始化；该历史问题没有在本轮文档工作中被复现或关闭。下一次涉及场景退出/资源生命周期的实现应核查它，不能因归档而从待办消失。

装备对比、模态层级和撤离确认的历史改动各有不同验证范围。对 v2 同一路径做改造时，复用适用用例重新执行，并补上新奖励、区域结束和具体物品候选的交互验证。真正的设备触控、微信宿主、正式美术、性能和数值体验仍需独立交付。
