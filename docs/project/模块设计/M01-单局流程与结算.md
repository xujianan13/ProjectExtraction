# M01 单局流程与结算

更新日期：2026-09-29。状态：设计草案，尚未实现；文中的类型和接口名均为拟议名称。

规则来源：[核心玩法设计](../核心玩法设计.md)。模块关系与开发顺序：[玩法模块与迭代计划](../玩法模块与迭代计划.md)。

## 1. 定位与已确认规则

本模块是整局状态和最终结算的唯一协调者，负责将入场、撤离、死亡和返回局外连接成闭环。

- 进入有效撤离点或角色死亡时，当局结束。
- 正常撤离：全部当前持有物品带回，包含入场装备、战利品和技能物品，不再选择 X 件。
- 死亡：安全箱外的入场装备和战利品全部丢失，安全箱内物品保留；技能物品同样遵守位置保护规则。
- 每次成功撤离获得经验，升级可解锁高等级关卡；死亡是否获得经验尚未确定。
- 安全箱默认容量 X 的含义与配置由 M06 管理，不能把 X 用于限制正常撤离携出数量。

## 2. 职责边界

| 本模块负责 | 协作模块负责 |
| --- | --- |
| 创建 RunId，校验入场准备，管理加载/游玩/结算等阶段 | M07 校验关卡解锁，M06 提供携入物品和唯一所属位置 |
| 接受当前局有效的死亡或撤离请求，冻结结束结果 | M03 提供玩家生命与死亡状态，M04 提供撤离点有效性 |
| 按结局协调物品与成长计划，形成统一存档候选 | M06 计算保留/丢失实例集合，M07 计算经验与解锁变化 |
| 确保一次提交、失败可重试、成功后开放局外操作 | 存档框架执行写入并返回确认结果，M08 显示当前状态 |
| 结束时停止业务并组织异步资源释放 | 各模块释放自身拥有的输入、事件、实例和资源租约 |

M01 不生成物品属性、不判断武器命中，也不让 UI 直接修改结算数据。局外仓库由 M06 管理；同一次结算的物品、经验和结算标识由 M01 统一组织保存。

## 3. 单局状态设计

下表是项目业务状态建议，需映射到既有 GameRoundFlow，不重写另一套通用转场框架。

| 阶段 | 允许的关键操作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 局外准备 | 选择已解锁关卡、装配、确认携入清单 | 关卡/物品校验通过，入场记录保存完成 |
| 加载 | 创建单局和房间内容，阻止重复开始 | 加载完成后进入游玩；失败走清理和入场恢复流程 |
| 游玩 | 移动、战斗、拾取、容器与商店交互 | 有效结束请求被接受后立即冻结 |
| 暂停（若采用） | 展示菜单，停止对应模拟 | 恢复条件和允许时机待定，暂停不等同于结束 |
| 结算中 | 显示冻结结果和保存状态；阻止再拾取、交易、出战 | 结果保存确认成功，且本局资源完成退出 |
| 结算失败 | 显示失败原因并重试原结果 | 成功后继续，不重新随机掉落或再次累计奖励 |
| 结果展示 | 查看物品去留、经验和解锁变化 | 返回局外，随后允许创建新的一局 |

局外准备可由项目入口承接，Flow 管理会话加载、退出和保存串行化。暂停、放弃、强退都不能未经规则定义转换成撤离或死亡。

## 4. 输入、输出与结算顺序

| 输入 | 输出 |
| --- | --- |
| 关卡 ID、携入清单、M07 准入结果 | RunContext：RunId、关卡、配置版本及本局上下文 |
| 当前局角色死亡事件 / 有效撤离请求 | 唯一冻结的 RunOutcome：结局、物品快照、成长计划及来源标识 |
| M06 物品计划、M07 成长计划、当前存档版本 | 同一份项目存档候选和保存回执 |
| 重试或返回局外意图 | 明确的阶段转换结果，供 M08 展示 |

建议正常路径：

1. 入场前，验证配置、关卡资格和携入清单；由 M06 将携入实例转入本局归属，并把入场记录与局外库存变化一并保存。未确认成功前不进入可操作战斗。
2. 加载失败时清理已创建资源，再恢复尚未开始游玩的入场记录；恢复也需确认保存后才开放物品操作。加载失败不自行算作角色死亡。
3. 收到结束请求后校验 RunId、角色和当前状态；M04 的刷点通知不能直接充当玩家已撤离。同一局只接受一个最终结果，其他请求返回已结束。
4. 停止战斗和物品变更，冻结 M06 的完整库存及位置快照；技能实例必须包含在快照中，不能随效果对象销毁而丢失。
5. M06 生成物品保留/丢失计划，M07 生成适用的经验与解锁计划。二者无独立结算写入。
6. M01 将两份计划、入场记录结束状态和已结算 RunId 合并成一个存档候选；先校验实例唯一性和集合完整性，再提交。
7. 等待存档确认。框架 Flow 退出会话在保存回调之前，故冻结结果需由项目结算上下文持有，不能依赖已经销毁的场景对象。
8. 保存成功后发布可操作的最终局外状态和结果界面；失败时保留同一候选及标识，关闭新增出战入口，按框架保存语义重试或查询不确定结果。

候选已经应用到保存模型时，重试只提交原修订，不再次加经验或再次移动物品。确切的模型发布方式在实现阶段选择，但物品和成长必须属于同一持久记录，不能出现“装备到账、经验没到”的半次结算。

## 5. 持久化与异常边界

- 建议项目存档包含物品状态、成长状态、当前入场记录、结算提交标识和 schema 版本；保存纯数据，不保存 Unity 对象或资源句柄。
- RunId 在持久化范围内唯一；重复回调、重试和返回流程不得产生第二份收益。旧局迟到事件不能影响新局。
- 正常重开档以确认写入的记录为准。已提交的结算不能重发；未完成入场或结算必须能够识别，不能把旧局外装备无条件恢复为另一份。
- 内存中的冻结结果不能保证在系统强杀后仍存在。异常中断需要采用继续本局、检查点恢复或其他明确政策，当前仍待定；在政策落定前不得宣称已支持崩溃恢复，也不得自行把中断视为撤离或死亡。
- 成功撤离若遇局外空间不足，仍须有完整接收方案；仓库容量及溢出形式交由 M06 设计，不能静默删除应带回物品。
- 同一模拟时段同时满足死亡与撤离时的胜出规则待定；技术实现需统一仲裁，不能让不同监听顺序随机决定结局。

接入参考：[关卡与单局流程](../../framework/关卡与单局流程.md)、[正式存档使用指南](../../framework/正式存档使用指南.md)。GameRoundResult 只包含通用结果字段，物品与经验详情应保存在项目自己的 RunOutcome 中。框架文档中的 Demo 存档不是当前项目已经实现的结算。

## 6. 最小交付与扩展

- **I2 最小交付：** 用固定测试关卡和可控撤离点完成携装入场、拾取、死亡、安全箱保留、正常全量带出、成功经验和再次入场；使用显式测试参数，不先确定 X 的正式值。
- **I3 / I4 接入：** 将测试房间换成 M04 的正式房间上下文，接入 M05 完整物品和 M07 等级解锁，不改变结算入口。
- **后续扩展：** 异常中断恢复、更多结算展示及统计，只在相应规则明确后增加。网络模式不在当前设计中预设。

## 7. 验收场景（待实现后执行）

1. 撤离携带入场武器、普通战利品和技能物品，返回后实例 ID、数量和随机值全部一致；不出现选择携出件数步骤。
2. 相同物品清单分别放在背包/装备位/安全箱后触发死亡，仅安全箱内实例保留；再次入场不能取回已丢失的旧装备。
3. 重复发送死亡、撤离或旧局事件，同一局最多产生一次终结和一次收益；新局库存不受影响。
4. 模拟保存失败、结果不确定和随后重试，成功状态只在确认为已保存后展示，物品和经验不重复发放。
5. 正常结算后关闭再打开存档，物品、等级、解锁状态和已结算标识一致；不以重新生成物品替代读回实例。
6. 加载失败、返回和连续开启多局后，资源与事件订阅无残留；未完成入场记录有明确恢复处理，不能留下可重复使用的装备副本。

## 8. 待定决策

死亡与撤离同时发生的仲裁、异常中断处理、主动放弃、暂停/后台规则、成功经验数值及死亡经验、安全箱操作约束、局外存储容量、全失后再次出战方式。入场真实存档闭环上线前必须先补齐相关规则。
