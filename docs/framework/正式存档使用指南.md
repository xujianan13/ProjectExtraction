# 正式存档使用指南

## 当前实现

框架新增 `ISaveModule` / `SaveModule`，源码位于 `DevProject/Assets/Scripts/GameFramework/Runtime/Modules/Save`。`GameEntry.RegisterDefaults()` 已注册模块。`IStorageModule` 继续保存轻量偏好，正式玩家进度通过 SaveSession 保存。

已提供 A/B 双槽、SHA-256 校验、逐版本迁移、独立迁移备份双槽、明确恢复确认、自动保存、串行写入、取消等待与不确定结果收束、同存储身份的进程内单写者保护。跨设备云同步与跨进程排他不在本版范围。

本次增加了宿主侧 `SaveModule` 和启动收尾 API，首次采用本版需要重新构建宿主安装包；只更新旧宿主的 GameLogic DLL 无法补齐这些 API。后续修改游戏 DTO/迁移可随 GameLogic 热更，发布时仍须设置包级最低宿主版本。

## 1. 配置平台后端

宿主内置的 `Resources/HotUpdateBootSettings` 增加 `Save Backend`：

| 配置 | 行为 |
| --- | --- |
| Auto | Editor/原生选择文件后端；WebGL 要求明确选择 |
| File | 使用 `Application.persistentDataPath/Saves`；WebGL 拒绝此模式 |
| BrowserIndexedDb | 标准浏览器 WebGL 使用 IndexedDB |
| PlatformSdk | 使用项目注入的小游戏 SDK 存储端口 |

游戏也可以在打开任何会话前显式调用：

```csharp
ISaveModule saves = GameEntry.Get<ISaveModule>();
SaveResult configured = saves.ConfigureBackend(new FileSaveBackend(customSaveDirectory));
```

必须检查返回结果。已经有会话或物理操作时，框架拒绝更换后端。

小游戏在启动前设置 `MiniGame.Boot.HotUpdateBootstrap.PlatformSaveStore`，提供 `IPlatformSaveStore`，并在宿主配置中选择 `PlatformSdk`。具体映射见 [SDK 接入模板](../../DevProject/Assets/Scripts/PlatformAdapters/README.md)。未安装/注入 SDK 时返回 `Unsupported`，不会退到内存存档。具体 Unity SDK 的 hide/show 应转接到存档会话 `OnBackground`；与 Unity 生命周期通知保持幂等。

## 2. 定义游戏数据

项目数据和迁移放在 `Assets/Scripts/GameLogic/Runtime/Save`；框架不引用游戏字段。内置样例为 `PlayerSaveData`、`PlayerSaveDefinition`、`PlayerSaveService`，保存累计攻击次数。

```csharp
[Serializable]
public sealed class ProgressData
{
    public int Level = 1;
    public int Coins;
}

var definition = new SaveDefinition<ProgressData>(1,
    () => new ProgressData(),
    data => data != null && data.Level >= 1 && data.Coins >= 0 ? null : "玩家进度无效");
```

校验函数返回 null/空字符串代表通过，非空字符串为失败说明。默认 codec 使用 `JsonUtility` 的 Type 重载；需要字典/多态时实现 `ISaveCodec<T>`。Unity 对象引用、资源句柄和服务对象不能进入 DTO。

每份存档以 `SaveIdentity(gameId, environment, profileId, slotId)` 隔离。身份片段按严格 UTF-8 校验并编码；不把游戏版本/AB 版本放入身份。样例 Editor 使用 `editor` 环境，Player 使用 `release`，用户与槽为 `guest/main`。登录游戏需自行绑定真实 ProfileId，不能自动合并游客数据。

## 3. 打开、恢复和激活

```csharp
var identity = new SaveIdentity("my-game", "editor", "guest", "main");
SaveOpenResult<ProgressData> opened = await saves.OpenAsync(identity, definition, ct: ct);
```

先检查 `opened.Result.Success`，成功后才使用 `opened.Session` 与 `opened.LoadResult.Data`。加载结果区分 `New` / `Saved` / `Recovered`，并提供 `Migrated`、`NeedsWrite`、`Sequence`。

打开不会写入。游戏复制 DTO 到内存模型，绑定返回独立快照的 `BindSnapshot`；如果来源为 `Recovered`，先提示并取得明确恢复选择，再调用 `AcceptRecovery`。初始化成功后调用 `Activate`；新建或迁移档需要等待 `FlushAsync` 首存成功再开放玩家进度。

现有样例启动为：

```text
Boot 配置后端并完成热更
→ GameMain 打开存档 / 确认恢复 / 初始化游戏
→ Boot CommitReady
→ GameStartupCompletion 执行 PlayerSaveService.CompleteStartupAsync
→ 激活、必要首存成功 → 解除玩法阻断 → 卸载 Loading
```

首存失败只重试项目收尾；不会重复加载 DLL。读取失败与未来版本/坏档有独立结果，不会静默创建默认档。

`GameStartupCompletion` 是项目启动收尾的共享契约。游戏在 `StartAsync` 注册回调并返回，宿主随后等待回调；不要在 `StartAsync` 里等待该回调，避免互相等待。

## 4. 修改与保存

持久数据修改后调用 `session.MarkDirty()`；绑定快照的业务对象要由主线程管理。所有模块与会话 API 也在 Unity 主线程调用。

默认策略：变化后空闲 1 秒合并保存；持续变化达到 10 秒发起保存；操作等待上限 10 秒；瞬时错误最多尝试 3 次。通过 `SavePolicy` 覆盖，打开时会复制策略。

```csharp
model.Coins += reward;
SaveResult changed = session.MarkDirty();
SaveFlushResult receipt = await session.FlushAsync(ct);
```

重要结算检查 `receipt.Result.Success`；普通变化依赖自动保存即可。Flush 保证调用时的目标修订号已保存，不承诺保存期间后续发生的所有变化都已落盘。

- `RetryAsync`：用户处理失败原因后重试；遇到不确定结果先核对候选，原写入未结束时不会发起第二次写入。冲突和未来版本错误需关闭并重新处理，不直接重写。
- `GetStatus` / `StatusChanged`：观察阶段、dirty、修订号、持久序号和最近结果。框架不直接弹通用错误窗口。
- `CloseAsync`：业务先停止进度修改，再等待最终保存与物理操作收束；失败时仍保留会话。
- `Dispose` / 模块关闭：同步停止调度，不等于保存完成。异步关闭前已经 Dispose 的会话不会返回虚假的保存成功。

框架已接 `GameEntry.ApplicationBackgroundChanged`；后台只作尽力保存，退出/被系统强杀时不保证能完成异步操作。平常自动保存和结算保存承担主要保障。

## 5. 增加数据版本

把当前版本升为 2，并声明从 1 到 2 的纯数据迁移：

```csharp
var migration = new SaveMigration(1, ValidateV1Json, MigrateV1ToV2Json);
var definition = new SaveDefinition<ProgressData>(2, CreateDefault, ValidateCurrent,
    migrations: new[] { migration });
```

`ValidateV1Json` 返回来源校验错误或 null，`MigrateV1ToV2Json` 返回新版 JSON。多个版本逐步运行，每一步进入下一版本的来源校验或最终 DTO 校验；缺迁移或校验失败就停止。

迁移先在内存完成。首次提交新版前，把来源完整旧记录保存到 `pre-migration/a|b` 并确认，再写常规 A/B。普通保存不修改迁移备份。备份槽固定两份，升级时轮换，保留最近升级来源。

旧程序遇到更高 schema 或未知封装格式会拒绝写入。热更包回退不等于存档自动降级。

## 6. 显式恢复到新槽

当坏档、未来版本或迁移失败需要查看备份时，先关闭相同身份的已有会话：

```csharp
SaveRecoveryInspection inspected = await saves.InspectRecoveryAsync(identity, definition, ct);
SaveOpenResult<ProgressData> restored = await saves.RestoreToNewSlotAsync(selectedCandidate,
    new SaveIdentity("my-game", "editor", "guest", "recovered"), definition, ct: ct);
```

先检查 `inspected.Result`，展示 `Candidates` 的来源、版本、序号与 `IsUsable`，由用户/项目策略明确选择 `selectedCandidate`。框架重新校验候选，并要求目标常规槽与迁移备份全部为空。恢复会话尚未激活；绑定快照、初始化、激活并保存后目标才落盘。来源档不变，非空目标返回冲突。

## 7. 存储布局与可靠性

逻辑键为 `saves/v1/<game>/<environment>/<profile>/<slot>/a|b`；迁移备份在同身份下的 `pre-migration/a|b`。

文件后端将完整逻辑键的 SHA-256 映射成根目录下的 `.save` 文件，避免深目录和路径长度限制。写入使用同目录临时文件、flush 与目标替换；不支持替换的平台仅写非当前槽。正常完成清理临时文件，中断残留 `.tmp` 不参与读取。记录自身仍校验完整身份，哈希文件名不能代替数据校验。

浏览器后端使用稳定数据库 `GameFramework.Save.v1` / `records`，完整记录按字符串写入。成功回调在 IndexedDB 事务完成后发送；一次请求先成功、事务后中止仍算失败。

默认完整记录上限 256 KiB。浏览器后端当前采用相同上限；其他后端可通过配置调整，实际有效上限取策略与后端限制较小值。A/B、迁移备份和临时文件都占用空间。读取超过当前上限的记录会阻止打开，不会把它当坏档覆盖。

## 8. 高频状态增量

`SaveStateJournal` 供完整记录后端上的高频状态保存使用，与 `SaveSession<T>` 的账号事务分别管理。业务将一个完整逻辑边界拆成稳定键的 `SaveStateComponent` 列表，`CommitAsync(identity, components)` 只写变化组件和删除键；首次提交及达到间隔后写完整检查点。两组数据区与两个提交头轮换，先确认数据块再确认提交头，恢复只接受连续且摘要完整的状态。

```csharp
var journal = new SaveStateJournal(backend, "my-game/profile/run-state", 120, 4 * 1024 * 1024);
SaveJournalLoadResult loaded = await journal.LoadAsync(runId);
SaveResult saved = await journal.CommitAsync(runId, components);
```

调用方持有唯一 FIFO 队列，并在入队时冻结组件内容。`HasPending` 表示原候选尚未确认，此时只能 `RetryAsync()`，不能用修改后的内存替换原候选。读取错误、未知版本、容量超限或无法恢复完整状态均需要显式处理；`Missing` 才表示没有该身份的提交。`UsedPreviousRevision` 表示最新提交不可用而恢复了先前完整修订。账号事务与日志共用后端时，业务还须串行排空日志再保存账号，关闭时等待在途操作。

`Revision`、`LastPayloadBytes`、`TotalWrittenBytes` 和 `LastCommitMilliseconds` 可用于诊断。组件结构和兼容版本由业务校验；日志不负责解释战斗、奖励或物品，也不提供离线补算。当前 Unity 测试覆盖分块、检查点轮换、损坏回退和同候选重试；这不代表各设备的吞吐或 WebGL 桥接成本已经验收。
