# 统一验收

`tools/verify.ps1` 是当前主工程与新项目复用链路的统一检查入口。运行前关闭正在使用相同 `DevProject` 的 Unity Editor；脚本会检查工程可用性、持有 `verification/verify.lock`，并将机器可读汇总写到 `verification/verify-result.json`。本次执行结果见[五项完善验收记录](五项完善验收记录.md)；旧的带日期验收记录是历史证据，不作为当前结果。

## 命令

在仓库根目录运行：

```powershell
# 默认 Quick：导表工具测试、表生成物校验、主工程检查和完整 PlayMode。
& .\tools\verify.ps1

# Full：在 Quick 后创建并验证 Minimal 隔离副本，完成脚手架、离线包和复用回归。
& .\tools\verify.ps1 -Mode Full

# 在 Full 基础上准备并构建 Windows IL2CPP Player，再运行真实进程启动探针。
& .\tools\verify.ps1 -Mode Full -WindowsPlayer

# Unity 或 HybridCLR 源码不在默认位置时指定路径。
& .\tools\verify.ps1 -Mode Full -WindowsPlayer -EditorPath 'D:\Program Files\Unity\Editor\2022.3.62f2\Editor\Unity.exe' -HybridClrSource 'D:\path\to\libil2cpp'
```

`-WindowsPlayer` 必须配合 `-Mode Full`。`-HybridClrSource` 用于指定兼容 HybridCLR 的本地 `libil2cpp` 源码，仅在 Windows Player 准备与构建阶段暂时设置 `MINIGAME_HYBRIDCLR_SOURCE`。脚本另有 `-TimeoutSeconds` 控制各 Unity 命令的超时，默认 1800 秒。Windows Player 需要 Unity 2022.3.62f2 Windows Build Support（IL2CPP）、MSVC C++ 工具链、Windows SDK 和当前项目的 HybridCLR 准备流程。命令还需要 Node.js、npm 与已安装的 `tool` 依赖。

## 检查范围

| 模式 | 阶段 | 实际检查 |
| --- | --- | --- |
| Quick | `node-tests`、`excel-verify` | 执行 `tool/*.test.mjs`，校验现有 Excel 生成物。 |
| Quick | `project-check`、`playmode` | Unity 批处理检查首次导入状态、导表、脚手架和 API 索引，再运行主工程完整 PlayMode。 |
| Full | `minimal-create`、`minimal-import`、`minimal-initialize`、`minimal-check`、`minimal-playmode` | 从 `-Template Minimal` 创建隔离新工程，完成首次导入、身份和 GamePackage 准备、项目检查与纯净内容 PlayMode。 |
| Full | `semantic-fixture`、`scaffold-generate`、`reuse-check`、`reuse-editor-playmode` | 在隔离副本添加语义 Excel 样例，运行脚手架生成，再检查 API、数据和 Editor 运行。 |
| Full | `reuse-offline-build`、`reuse-offline-playmode` | 构建离线 GamePackage 并运行对应 PlayMode。 |
| Full + Windows Player | `player-probe-install`、`player-prepare`、`player-build`、`player-smoke` | 仅向隔离副本注入 Boot 探针，分开准备 HybridCLR 与构建 Player，运行独立进程观察真实启动状态。 |

`Minimal` 保留 Main/Loading、固定 Boot 热更入口和输入，移除三关演示及 PlayerSave 业务；首次导入通过正式脚手架生成空 `Main` 玩法、`Home` Page 窗口及 Prefab 模式的 `Home` 逻辑场景。空 Excel 目录可生成可编译入口；新玩法已有普通帧、固定帧和帧末钩子，见[玩法更新阶段](玩法更新阶段.md)。UI 重复项的窗口接入见[UI 虚拟列表](UI虚拟列表.md)。

## 日志、结果与隔离边界

固定结果文件为 `verification/verify-result.json`，包含 `schemaVersion`、`mode`、`windowsPlayer`、`success`、开始和结束 UTC 时间、`failedStage`、`error` 及逐阶段 `name`、`success`、`seconds`、`details`。进入阶段执行后，即使某阶段失败，脚本也在 `finally` 写入该文件；Editor 路径与工程占用等前置检查也会记录失败；参数绑定或取得运行锁之前的失败仅返回错误，以免覆盖另一个正在运行的验收报告。Unity 阶段日志按 `verification/<阶段名>.log` 保存；PlayMode XML 为 `verification/playmode.xml`、`minimal-playmode.xml`、`reuse-editor-playmode.xml`、`reuse-offline-playmode.xml`。Node 日志另有 `node-tests.log`、`excel-verify.log` 与 `semantic-fixture.log`。

Full 的临时工程固定在 `verification/unified-reuse`。脚本仅在路径精确匹配、目录不是重解析点、存在内容为 `UnityMiniGameFramework verification copy v1` 的 `.framework-verification-copy` 标记、且对应 Unity 工程未被占用时，才会删除旧副本重建。非标记目录或用户目录会被拒绝删除。`new-project.ps1 -AllowNestedVerification` 只允许在仓库 `verification` 子目录建立受控副本；普通新项目应使用仓库外的空绝对路径。失败后的隔离副本留在原处供检查；不要把它当作正式项目。

Windows Player 的固定输出是副本中的 `DevProject/Builds/Windows/Game.exe` 和构建报告。Player 探针采用 `-batchmode -nographics`，用于验证原生启动与逻辑状态；图形效果需要另行在图形模式检查。启动日志为 `verification/player-smoke.log`，探针 JSON 为 `verification/player-smoke.json`。探针仅在独立 Player 收到 `-frameworkSmokeResult <Windows 绝对路径>` 时安装；Editor 不运行。它最多等待 90 秒未缩放时间，要求框架已启动、`HotUpdateBootstrap.HasLaunchedGame`、Loading 已卸载、逻辑场景活动且至少一个业务窗口可见。JSON 记录 `success`、`error`、Unity `scenes`、`logicalScene`、玩法 `gameplay` 数量、可见 `windows`、耗时 `time` 及启动状态，并以退出码 0/1 表示成功/失败。

统一验收只覆盖脚本所列的本地导表、Editor、隔离新工程、离线内容包，以及启用开关时的 Windows IL2CPP Player；真实 CDN、WebGL 和平台 SDK 仍按各自环境另行验收。只有对应日志和结果文件完成后，才在验收记录中填写通过数量与结论。
